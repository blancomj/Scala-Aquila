#### Design Specificity Verdict

**Partially specific — real domain modeling, inconsistent visual execution.**

**LLM assessment**: The module is unmistakably Aquila-specific in its information architecture — `rubros`, `fuentes de financiación`, the reconciliation logic in `PresupuestoTabControlValidaciones.vue` mirroring actual Postgres guard triggers, a 4-cell cycle tracker built around this product's specific budget lifecycle rather than a generic progress bar. Where it stops being specific is the visual execution: two of the tracker's four cells lean on raw `text-green-600`/`text-amber-600` instead of routed semantic tokens, and the tracker sits in a `rounded-lg` container when DESIGN.md reserves that radius for "large feature modules," not a thin status strip.

**Deterministic scan**: `detect.mjs app/pages/presupuesto` → exit 2, 4 findings, all `design-system-font-size` (advisory): `index.vue:159,166,173,183`, the four cycle-tracker cell captions using a literal `text-[10px]` instead of the DESIGN.md type ramp. `detect.mjs app/components/presupuesto` → exit 0, clean. No false positives — both agents independently confirmed the flagged elements render exactly as described. Notably, the detector's rule set does not check color-token drift (`gray-*` vs `neutral-*`), so it caught the font-size literals but missed the far larger token-compliance issue the LLM review found by reading source directly — a real example of the two assessments covering different ground rather than duplicating it.

**Visual overlays**: Overlay-script injection was deliberately skipped — this is a real authenticated, multi-tenant Nuxt app, and injecting a second static server's `detect.js` into the live session risked losing the Supabase session for no new signal beyond what the CLI scan already gave. In its place, Assessment B ran a full manual live inspection instead: logged in via the project's own magic-link dev flow, switched to a tenant with real budget data (GC-001, presupuesto 2026 v2/v1), and visited all 6 tabs plus both sibling pages at desktop width, then re-tested at 375×812 with actual DOM measurements (not just a screenshot read). This is stronger evidence than a static overlay would have produced, and it's where the two most substantive findings in this report — the cross-page numeric mismatch and the sidebar's total absence of mobile collapse behavior — came from. There is no `[Human]`-tab overlay to view; the findings below are reported directly.

#### Overall Impression

The information architecture and domain modeling here are the real thing — reconciliation logic, source-account linkage warnings, versioned budgets, all grounded in how PH budgeting actually works. What undermines it is finishing: a design-token migration that visibly stalled mid-file, a tab component that got half the ARIA pattern right and the interactive half wrong, a complete absence of the one feedback mechanic DESIGN.md mandates for every save, and — found only by actually logging in and clicking through with real data — a reconciliation page that tells a different number than the page next to it. The single biggest opportunity is closing the gap between "the rules exist in DESIGN.md" and "the newest module in the app follows them," because right now this freshly-redesigned surface is also the one most out of compliance with its own governance file.

#### What's Working

1. **Badge/status color routing is done right.** `presupuesto-labels.ts:14-19` routes `COLOR_ESTADO_PRESUPUESTO` through `neutral`/`primary`/`success` with no hardcoded hex — same discipline in `PresupuestoTabPeriodosVigencia.vue:49-60` for periodo states, including correct use of `error` for `bloqueado`.
2. **Select vs. searchable-select discipline is followed correctly everywhere it appears.** Every drawer uses plain `<USelect>` for short catalogs and `<UiSelectorBuscable>` specifically for the long cuenta catalog (`PresupuestoEjecucionDrawer.vue:180,223`, `PresupuestoRubroDrawer.vue:147`, `PresupuestoFuenteDrawer.vue:117`) — DESIGN.md's rule applied correctly, component by component.
3. **The cycle tracker is genuine product design**, not a template — it answers "where am I in this cycle" without cross-referencing three tables, and correctly codes status by color *and* glyph, not color alone. Live-verified: on real GC-001 data it rendered all 4 states correctly.

#### Priority Issues

**[P0] The hand-rolled tab nav is a keyboard trap.** `index.vue:198-216` builds `role="tablist"` with correct `aria-selected` and roving `tabindex` (`0` on the active tab, `-1` on the rest) — but there is no `@keydown` handler anywhere in the file (confirmed by grep: zero matches for `keydown`/`ArrowRight`/`ArrowLeft`). With `tabindex="-1"` on five of six buttons and no arrow-key handler to move the roving index, a keyboard-only user reaches exactly one tab and then Tab carries them straight past the tablist into panel content — five of six tabs (Plan de cuentas, Fuentes, Ejecución, Coeficientes, Simulación) are unreachable without a mouse. This fails the WAI-ARIA APG tab pattern by implementing the state half and skipping the interaction half. **Fix**: add `@keydown` on the tablist for `ArrowLeft`/`ArrowRight` (wrap-around) and `Home`/`End`, moving both focus and `tabActiva` together (matching the existing click-driven automatic-activation model). **Suggested command**: `/impeccable harden`

**[P0] The reconciliation page disagrees with itself.** Live-verified on real data (GC-001, presupuesto 2026 v2, $1.000.000): `/presupuesto/control` shows "Rubros de egreso = Monto total del presupuesto" as **`$0 ≠ $1.000.000`**, while `/presupuesto`'s own cycle tracker shows the identical comparison for the identical budget as fully reconciled — green check, "$1.000.000 de $1.000.000." For a product whose first stated principle is "financial correctness is non-negotiable... full audit trail," a page whose entire job is telling staff whether their budget reconciles cannot show `$0` on one screen and a matching total on the next for the same number. Whether this is a stale/uninitialized read on the control page or a genuine logic divergence between the two computations needs engineering triage — but as a design-review finding it fails heuristic 1 outright: the system's status is not just unclear, it's contradictory. **Fix**: trace `PresupuestoTabControlValidaciones.vue`'s rubro-total computation against the one `index.vue` uses for the same comparison and reconcile them. **Suggested command**: `/impeccable audit`

**[P1] Silent success on every consequential action.** Zero `useToast()` calls anywhere in `apps/web/app/components/presupuesto/` (grep-confirmed across all 12 files). Activating a presupuesto (explicitly described in its own confirmation copy as making the budget immutable), creating a rubro/cuenta/fuente, and reverting an execution movement all close their modal/drawer and update the table with no explicit confirmation — directly against DESIGN.md's stated rule ("useToast() confirms an action completed... never silence after a 'Guardar' click") and PRODUCT.md's traceability principle. The dead `cargando` ref in `PresupuestoTabControlValidaciones.vue:14` (set, never read in the template) is the same category of gap. **Fix**: wire `useToast()` on the success paths in `PresupuestoTabPresupuestos.vue` (`confirmarActivarPresupuesto`), `PresupuestoTabPlanCuentas.vue` (`guardarMonto`, `alternarActiva`), `PresupuestoTabEjecucion.vue` (`ajustar`), and the four drawers' create/edit handlers. **Suggested command**: `/impeccable harden`

**[P1] Design-token governance drift, worst inside the module's own newest file.** Two independently-sourced findings converge here. The LLM review found extensive raw `gray-*`/hardcoded `green-*`/`amber-*` usage across 9 of the module's files (`index.vue:123,159,166,173,183,198,206,210`; `control.vue:25`; heavy repetition in `PresupuestoTabPlanCuentas.vue`, `PresupuestoTabFuentes.vue`, `PresupuestoTabEjecucion.vue`, `PresupuestoTabSimulacion.vue`, `PresupuestoTabControlValidaciones.vue`) against DESIGN.md's explicit "no new gray-* is accepted" rule — most damning in `periodos.vue`, where the header (line 25, `text-gray-500`) uses the old system while the rest of the same file (lines 67-112) consistently uses `text-neutral-500`/`border-neutral-200`, meaning the drift is inconsistent within one component, not just legacy debt. The detector independently caught a different, non-overlapping slice of the same governance problem: 4 literal `text-[10px]` font sizes off the type ramp (`index.vue:159,166,173,183` — the same lines, different rule). Together they show the detector's rule set doesn't cover color-token drift at all, which is exactly the kind of gap dual-assessment is supposed to surface. **Fix**: sweep `gray-*` → `neutral-*` across the 9 files cited, route `border-green-200 bg-green-50/50`-style pairs through semantic classes, and pull the tracker captions onto the DESIGN.md type scale. **Suggested command**: `/impeccable audit`

**[P1] Mobile is functionally broken, and not for the reason it looks like from the source alone.** Live-measured at 375×812 (not reasoned from classes): the app shell's sidebar has no mobile collapse behavior at all — no hamburger toggle exists anywhere in the header, and the `<aside>` permanently occupies 224px of a 375px viewport, leaving `<main>` a 151px column. Every presupuesto page/tab tested (Presupuestos, Plan de cuentas, `/presupuesto/control`) showed the identical squeeze: the header text wraps character-by-character, the cycle tracker's 4 cells (each individually responsive-correct, `grid-cols-1 sm:grid-cols-4`) get ~95px each and wrap mid-word, and the tab strip (also correctly built with `overflow-x-auto`) shows barely a fraction of one 6-tab label at a time. This is a layout-shell defect (`apps/web/app/layouts/default.vue`), not a presupuesto-specific bug — but it makes every finding below the fold in this module unreachable on a phone. Separately, and independent of the sidebar: `PresupuestoSelector.vue:29` sets a fixed `w-[28rem]` (448px) inside a non-wrapping `flex items-start justify-between` header on all three presupuesto pages — even in a properly-collapsed layout, a 448px fixed element next to a title in a non-wrap flex row does not fit a 375-414px screen; both defects compound today. **Fix**: add mobile sidebar-collapse behavior to the shared layout (app-wide fix, likely the highest-leverage single change available); independently, make the selector `w-full sm:w-[28rem]` or add `flex-wrap` to the three header containers. **Suggested command**: `/impeccable adapt`

#### Persona Red Flags

**Alex (Impatient Power User)**: Silent success amplifies for a power user specifically — activating a presupuesto and creating three rubros in a row gets zero positive confirmation on any of them, so she'll re-check the table out of doubt after every action, the opposite of the speed she wants. No bulk actions exist on any table (reverting three misregistered execution movements is three separate round-trips). Excel export exists only on the Ejecución tab, nowhere else in the module. And per the P0 above, tab switching is mouse-only — disqualifying for a self-identified keyboard-first user.

**Sam (Accessibility-Dependent User)**: The P0 tab-nav keyboard trap is her most severe blocker — five of six tabs are unreachable without a mouse. Status glyphs in `PresupuestoTabControlValidaciones.vue:167-189` render as bare Unicode characters (checkmark/cross/ellipsis/dash) with no `aria-label` override — a screen reader gets the raw glyph or nothing meaningful, not "Cumple"/"No cumple." On the positive side, icon-only buttons elsewhere in the module (chevron expand/collapse, add-subcuenta, activate/deactivate) carry `aria-label` consistently — that discipline shouldn't get lost fixing the rest.

**Casey (Distracted Mobile User)**: Confirmed, not hypothetical — live-measured at 375×812, the sidebar eats 60% of her screen with no way to dismiss it, the page title wraps into single characters, and reaching 5 of the module's 6 tabs means scrolling a ~95px-wide window sideways through an 891px-wide strip. This isn't "cramped," it's the module being effectively unusable one-handed on a phone, and the root cause (the app shell, not this module) means fixing it has to happen above the presupuesto code.

#### Minor Observations

- Visual hierarchy: the cycle tracker's color+glyphs pull the eye before the plain-gray page title — first glance lands on the status widget, not the page identity.
- `control.vue:26-27`'s description ("frente a los guard triggers reales de Postgres") is backend implementation vocabulary in user-facing copy — rewrite in plain terms.
- `PresupuestoTabPlanCuentas.vue:647` uses `color="error"` on a reversible deactivate toggle (a matching reactivate icon sits right next to it) — slightly overstates the stakes versus DESIGN.md's "error reserved for irreversible actions."
- `variant="soft"` appears repeatedly for primary-ish actions (`PresupuestoTabPresupuestos.vue:173`, `PresupuestoTabPlanCuentas.vue:521`) — a real Nuxt UI variant, but a fifth button pattern DESIGN.md's Buttons section doesn't document alongside `solid`/`outline`/`link`/`error`.
- Header pattern is inconsistent across the three pages: `index.vue` shows a status badge next to the selector; `control.vue`/`periodos.vue` don't, despite viewing the same selected presupuesto.
- The tracker's outer container uses `rounded-lg`, reserved by the Contained-Radius Rule for "large feature modules" — `rounded-md` matches a thin status strip's actual role.
- Ejecución tab's movement search has no visible clear/reset affordance.
- One apparent double-active-tab sighting on the Coeficientes screen was investigated and ruled out via DOM inspection — a screenshot misread, not a real bug; noted so it isn't mistaken for a finding later.
- Dev-console warnings seen during login/dashboard navigation (`NUXT_E3006`, an `import.meta.hot.send()` notice) are generic SSR/Vite hygiene noise, not presupuesto-specific, and not user-visible.

#### Questions to Consider

- If activating a presupuesto is genuinely irreversible and legally consequential (Ley 675 art. 47), is the silent-close-on-success pattern a real oversight, or a deliberate "the modal closing is confirmation enough" call worth revisiting explicitly?
- Given `periodos.vue` shows both the old and new color-token systems inside one file, is there an in-flight token migration for this module that stalled — and does finishing it touch shared components like `UiTabla.vue` that other modules also depend on?
- The `/presupuesto/control` vs `/presupuesto` numeric mismatch reads like a real bug, not a design issue — worth a quick engineering look before anything else on this list, since a reconciliation page that contradicts itself undermines trust in every other number in the module.
